# claude

> [!IMPORTANT] 最重要一点
> 给`Claude`验证工作方式，以便能够让它根据验证流程进行改进，最终产出质量翻倍，因此需要把精力放在验证机制做扎实，这样投资回报率最高。

## plugins/skill/agents

- plugins 一些系列`skill`和`sub agents`集合
- skill 用于扩展`LLM`在特定任务上的能力，例如ui/ux skill
- agents 任务专家，专门处理特定任务，用于任务并行（不关心上下文具体细节情况），例如代码审查agent、安全审查agent两者不关心各自具体上下文因此可以并行处理

三者都可以自动触发和手动触发。

[official-plugin](https://github.com/anthropics/claude-plugins-official/tree/main)

[officialMember-skill](https://github.com/ComposioHQ/awesome-claude-skills)

:::

## LSP

`LSP`一种开放协议，定义IDE与LLM之间的通信标准。`-lsp`添加的时候提供了整个项目的地图和语言级语义分析，为`LLM`提供项目索引、符号查询、依赖追踪等，使得能够精确跳转定义、查找引用等。

而且没有`-lsp`的时候，想要定义到具体逻辑的时候，`LLM`会去搜索文件，以此找到相关逻辑和影响，但这很可能会漏掉依赖特别是模块间依赖，同时会去加载整个项目导致思考时间长Token使用多(没有特定按需加载，也就是只加载对应模块和代码)，造成逻辑缺失。

::: tip 提示
`-lsp`前面加上`-`，这里是指的是已经提供了`LLM`的特定场景支持。例如`typescript-lsp`等等。
:::

## 总线型团队模式

::: warning 单体AI开发缺点
原始传统单体AI承担多种不同领域任务，被施加上了过多期望，同时还受到上下文限制、注意力限制的问题，导致任务处理变得降智，同时解决多种不同任务会参杂多种知识，逻辑紊乱造成逻辑断层。

这种模式缺点在复杂任务处理时非常明显，当对话超过上下文时模型会尝试去压缩上下文，导致原始上下文具体细节缺失以及逻辑变得模糊，最终使得任务处理效果不好。
:::

因而在复杂任务处理场景下可以使用`总线型团队模式`，类似网络架构设计中`总线`，具体使用如下:

```md
prompt:
【具体需求】, 创建并初始化以下4个sub agent，
其中架构师负责需求分析、技术选型、生成计划，
构建师负责代码编写、依赖管理,
验证者负责编写测试用例、bug追踪充当项目质量门禁，
最后是记录员负责编写使用说明、API文档。
```

::: tip 提示
这里的`总线型团队模式`是AI充当主节点对任务进行拆解、分发给不同特定领域`sub agents`每个agents负责处理特定任务、处理完后最后进行汇总。

但是这种模式的使用token成本很高，传统只有一个AI消耗token，现在变成了好几个，token使用翻好几倍。

:::

## 开发闭环

::: tip 重要
开发流程要重视**测试闭环**，也就是

```md
┌─────────────┐
│ 开发 │ ← authority + role + constraint
└──────┬──────┘
│
▼
┌─────────────┐
│ 测试 │ ← test（自测命令、验证步骤）
└──────┬──────┘
│
▼
┌─────────────┐
│ 验证 │ ← 检查输出是否符合预期
└──────┬──────┘
│
▼
┌─────────────┐
│ 优化 │ ← iteration（分析失败、调整策略）
└──────┬──────┘
│
└──────► 回到开发，直到通过
```

在准备开始写代码之前，生成的计划书中要第三人去审查避免单个AI主观因素影响造成细节和环节的遗漏，例如`审查这个计划文件`。这些文档最好物理存储，如果上下文被压缩之后文档具体细节和方案就会缺失，存储之后每次AI写完代码上下文不够压缩的时候，就可以根据这些文档继续下一步方案。

主要注意的就是还要`Git`可回溯，当前实施进度，避免中途开发跑偏(任务规划师)。还有一点就是在闭环中AI去修复代码时，需要明确一点**同时修复后必须验证问题已经解决，不能只改代码不测试**。

:::

::: warning 注意
上述过程跳过了`PRD`直接到开发技术文档(实施方案)，实际上需要进行需求验证验证**可行性**，然后在是技术选型、方案设计、实施方案。
:::

::: danger 危险
在进行迭代修复和自我改进过程中，可能会遇到报错问题，此时需要明确禁止它盲目重试，这里可以先让AI进行修复**2-3**次之后，后面还报错的话，就必须让它**停下来**思考并分析具体原因，然后再执行循环迭代过程。
:::

同时在AI编写完代码之后如果不想手动执行代码格式化工作，可以在`.claude/settings.json`中`claude hooks`定义相关hooks，例如在AI修改文件之后自动格式化代码:

```json
{
   "hooks": {
      //工具执行后使用
      "PostToolUse": [
         {
            "matcher": "Write",
            "hooks": [
               {
                  "type": "command",
                  "command": "pnpm run format"
               }
            ]
         }
      ]
   }
}
```

## 迭代循环安全

在使用Ralph Wiggum插件去基于开发流程循环进度开发的时候，默认是无限制迭代直到任务完成。

这样会不安全，特别是如果当它陷入到思考回环的时候特别危险，因此实际上操作使用时会限制循环迭代次数。

命令选项:

- `max-iterations <n>` -在n次迭代后停止
- `--completion-promise <text>` -标识完成的短语
- `/cancel-ralph` -手动取消循环

同时还需要确认完成标准，包含清晰完成条件和输出完成标准以及失败后的处理(卡住时的处理方法)，例如

```markdown
# cli使用

/ralph-loop "参考task.txt文件的详细需求" --max-iterations 20 --completion-promise "COMPLETE"

## task.txt

完成功能 X.

需求:

- 功能必须做 A, B, C
- 所有测试必须通过
- 代码覆盖 > 80%

如果15轮循环还是没有完成:

1、记录失败的内容：

- 你试过了什么？
- 具体错误消息
- 为什么你认为它失败了

2、研究替代方案

- 查找2-3个类似的实现
- 请注意使用不同办法

3、问题基础

- 这个抽象层次是否恰当？
- 这可以拆分为更小的问题吗？
- 有没有更简单的办法

4、尝试不同的角度

- 不同的库/框架功能？
- 不同的架构模式?
- 能否减少抽象而非增加？

**关键原则**

- 及时止损：不要重复相同失败
- 增量学习：每次失败都有记录
- 方向切换：从"加法"转向"减法"或"换法"

输出 <promise>COMPLETE</promise> 当完成的时候.

## 注意事项

上述cli使用之所以要在文件中列出详细需求，主要就是解决和避免包含换行符时，这个Ralph-loop插件在处理多行提示词时会触发安全错误
```

## 规则

[参考](https://github.com/TTT1231/claude-rules)

这里的规则是指在`claude.md`这样的系统提示词文件中，本质上是提示词工程。这个文件`claude.md`最好使用XML标签格式，因为官方示例在广泛使用，主要是XML标签提供清晰的层次结构，让claude能够识别不同规则的边界和作用域，也是解决在全局的`claude.md`中内容非常多的时候，XML标签让规则更容易定位、修改和调试。也即`XML+Markdown`这种格式最好。

::: tip 提示
这种适合在一个`CLAUDE.md`中内容特别多情况，别过度嵌套了XML结构，保持单层扁平即可，同时标签名称也别过长或含糊不清。

如果比较简单的话，就可以不用，直接使用markdown格式就可以了。
:::

当所有内容都嵌入了在一起导致`CLAUDE.md`内容很多，claude提供了`.claude/rules/`目录来解决这个问题。例如错误教训规则，使用如下:

```md
.claude/rules/
├── errors-learn/
│ ├── typescript-errors.md
│ ├── vue-errors.md
│ ├── api-errors.md
│ └── database-errors.md
└── testing.md
```

使用时直接在`CLAUDE.md`导入这条规则即可`TypeScript @.claude/rules/errors-learn/vue-errors.md`。

::: warning 注意
文件导入文件在导入文件规则为递归导入，默认最大深度为5层。

要根据项目所有技术栈相关程度，按照规则**优先级**进行导入和标记，例如标记高优先级错误经验规则:

```md
## [高优先级] 错误经验规则名称

原因: ....
解决: ....
预防: ....
```

然后将这个错误经验规则按需导入到项目的CLAUDE.md配置中即可`@.claude/rules/[path]/[to]/[target].md`

:::

## 过度多专家分工设计负债问题

在当前Agent领域"大而全"趋势下，如果违背了工程化落地的核心原则：解决实际问题的最小可行性方案，远胜于功能复杂但增加更多失败点的方案。这种复杂性不是价值，而是技术负债。

主要体现在多Agent调试成本指数增长，各Agent上下文被隔离传递时只保留了执行消息，同时开发时支持了所有场景和架构过度设计造成：学习成本陡峭、后续维护和迭代更慢。

因此实际好的设计应该时使用最小部件，稳定地解决真实问题，以解决任务为导向。

::: tip 提示
因此应该根据问题复杂度选择合适方案，大多数任务单Agent+skills就比多Agents协作更高效。也就是实用主义优先。

如果是阶段任务例如A、B、C可以任务并行而且任务边界清楚就可以用到多Agents，每一个agents负责对应任务互不干扰。
:::

## worktree

`Git Worktree` 允许在同一个仓库中检出多个分支到不同目录，而后管理这个`worktree`目录即可，在这个目录中跟`Git`一样使用即可，最后在合并到主分支即可。

claude结合`worktree`可以实现并行任务并发，从而单个任务失败或者成功在不合并到主分支之前，对主分支不会造成任何影响。

**基础命令**

| 命令                                        | 描述                       |
| ------------------------------------------- | -------------------------- |
| `git worktree add .trees/[feature-name]`    | 创建新的 worktree          |
| `git worktree list`                         | 列出所有 worktree          |
| `git worktree move <old> <new>`             | 移动 worktree 到新位置     |
| `git worktree remove .trees/[feature-name]` | 删除 worktree 及其引用     |
| `git worktree prune`                        | 清理已删除的 worktree 引用 |

**完整工作流示例**

假设需要同时开发两个独立功能：用户认证和支付集成

```sh
# 步骤1: 创建两个 worktree
git worktree add .trees/feature-auth -b feature/auth
git worktree add .trees/feature-payment -b feature/payment

# 步骤2: 查看已创建的 worktree
git worktree list

# 步骤3: 分别在两个终端中打开 Claude，针对不同目录工作。在各自worktree中正常使用Git等命令。

# 步骤4: 功能完成后，合并回主分支。然后清理已完成的worktree
```

**工作流最佳实践**

::: tip 提示

1. **统一目录命名**: 使用 `.trees/` 前缀组织所有 worktree，方便管理
2. **及时清理**: 任务完成后及时删除 worktree，避免累积过多目录
3. **独立终端**: 每个 worktree 使用独立的 Claude 终端，避免上下文混乱
4. **原子性**: 每个 worktree 专注单一功能，保持任务边界清晰
   :::

::: warning 注意
手动删除分支文件之后，分支引用还是会存在，这是还需要去git中删除这个分支引用。

`git worktree remove .trees/[feature-name]`。

最后别忘了分支还是存在的，还是需要手动去删除`git branch -d .trees/[feature-name]`
:::

## 重新规划计划

::: tip 核心原则
遇到问题时，**Claude 先自我审查判断严重程度**。如果是小问题，自主尝试修复 3-4 次（每次必须用不同方法）；如果判断无法修复，直接进入 **plan** 模式，重新探索新的方向，避免在错误方向死磕。修复失败后再由人介入决策。
:::

```
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  步骤1：创建终端
  ┌─────────────────────────────────────────────────────────────────┐
  │  人类根据任务复杂度决定终端数量：                               │
  │                                                                 │
  │  简单任务 → 开 1 个终端（终端 A）                               │

  └─────────────────────────────────────────────────────────────────┘

  │  人类阅读两个终端的输出                                         │

  步骤6：出现错误

  │  终端 A 输出：                                                   │
  │  "❌ 测试失败 / 编译失败 / 运行时错误"                           │

  │         ↓                                                       │
```

::: tip 自主修复的关键规则

-  1. **每次修复必须使用不同方法**
-  2. 尝试前说明："这次我用 X 方法，因为..."
-  3. 如果发现自己没有新方法了 → 立即报告人类
-  4. 3-4 次后仍失败 → 必须暂停，不要再试（大概率是方向出错因此需要及时止损）

- ✅ 每次尝试明确说明使用的方法和理由
- ✅ 尝试修复完成更新`CLAUDE.md`文档
- ✅ 遇到方向性问题直接进入 plan
- ✅ 修复后必须验证问题已解决

## 提示技巧

让AI扮演严格的**代码审查者**角色，让它“质疑你的决策”，让AI主动找问题、挑毛病而不是等了出错了在修复，把质量保证阶段落地到开发阶段。或者告诉它，证明给你看，这行得通，同时有实际的对比效果相较之前，例如缓存分支与主分支相比是否提升了性能。

::: code-group

```md [code-inspector.md]
你是我的缓存分支功能的**严格代码审查员**。请按照以下流程审查我的改动：

═══════════════════════════════════════════════════════════
第一步：代码审查
═══════════════════════════════════════════════════════════
阅读缓存分支上的所有改动挑战我的设计决策，找出

- 潜在bug和边缘情况
- 安全问题（如缓存穿透、雪崩）
- 性能瓶颈
- 代码可维护性问题
- 其他我没有考虑到的情况和问题，例如并发场景下的缓存一致性问题、缓存失效策略是否合理、Redis连接池配置是否优化合理等等

═══════════════════════════════════════════════════════════
第二步：效果验证
═══════════════════════════════════════════════════════════
1、对比main和缓存分支，运行相同测试记录结果
2、对比两者的差异，证明缓存确实生效例如缓存事件是否显著降低、命中与未命中行为是否符合预期、数据一致性是否保持一致

═══════════════════════════════════════════════════════════
第三步：最终结论
═══════════════════════════════════════════════════════════
只有满足以下条件才允许我提交PR：

- [] 所有严重问题已修复
- [] 性能提升有数据证明
- [] 缓存行为验证通过

---
```

:::

如果针对一个需求，在采取了不尽如意的补救措施，还是达不到现有的效果，直接进行**解决方案回退**。例如：“鉴于你现在所掌握的所有信息，放弃这个方案，实施更优雅的解决方案”，避免在一个错误方案上越走越远，浪费token。

::: tip 提示
在准备推送到生产仓库之前，应该要编写详细的规范并减少歧义。越具体，最后的更改成本就越少。
:::

## playwright 验证注意

如果是页面测试需要AI操作浏览器的，如果使用的是playwright等，这在AI场景方面就不适合使用，里面的HTML标签和样式会浪费很多Token和干扰AI上下文，同时还有dom节点操作也是还要去关心无关dom节点。

::: tip 提示
这里就可以使用[agent-browser](https://github.com/vercel-labs/agent-browser)代理服务器进行操作，进而简化HTML标签抽象层，过滤不需要对象将dom树转化为简洁的语义操作的可操作对象。
:::

## agent teams 协作

多智能体协作，在使用时需要考虑的是使用场景，什么场景下需要什么场景下又不需要。由于多agent teams在工作
时会通过主lead进行任务分发并统筹team的工作任务下发和任务进度的推进工作，因此如果任务太小的话那么会存在主lead协调
开销，此时速度就会慢一些而且协调工作意义不大。

还有一种情况就是大任务直接进行工作，例如重构整个代码库，这样
长时间独立工作如果方向错了或者claude遇到没有注意的情况会浪费大量时间和token。

创建agent的时候也需要考虑最小agent单元（最小团队规模），每一个agent专注一个特定领域，除了一些辩证和急需纠错、纠缺陷的场景。

::: tip 提示
因而最重要的是就是要明确最小交付物的独立单元，也就是任务独立完成不依赖其他完成工作并且同时还能
够完成后就能看到具体结果和快速检查是否完成正确。

让每个agent保持更加高效，结合官方文档任务5-6个就可以了。

任务开始时，可以`Ctrl + T`查看任务执行清单。
:::

::: warning 注意
分配太多任务的话，会增加主lead的协调负担，特别是在某个agent卡住的时候会让重新分配变得很困难。
同时任务越多token使用也会越来越多。

同时在权限配置中，主lead应该只关注任务的推进情况，只做协调者和分配者，不做执行者，这样让职责更加清楚和明确，
因此在开发时注意开启委托模式。

工作完成后要及时清理团队资源，否则会浪费token。
:::

> [!IMPORTANT] 最佳使用场景
> 在一些问题处理中，如果遇到问题找不到一个合理解决方案时就可以使用**辩证理论**，这样就很大程度上
> 避免了单个agent陷入思维定势，让不同agent从不同视角去分析问题并彼此之间相互论证，在假设不断被互相推翻的时候留下
> 来的假设往往是解决方案，这样就使得错误更早被发现减少单一视角的局限性错误。
>
> **例如:**
>
> ```md
> 创建一个agent teams去审查缓存功能，生成三个审查者进行审查:
>
> - 一个注重安全影响
> - 一个检查性能影响
> - 一个验证测试覆盖率
>   各自审查并报告结果。
> ```
>
> **彼此论证:**
>
> ```md
> 创建一个agent teams去审查缓存功能，生成三个审查者进行审查:
>
> - 一个注重安全影响
> - 一个检查性能影响
> - 一个验证测试覆盖率
>   各自先审查并各报告各领域发现的问题和改进建议，然后彼此质疑交叉论证并提出顾虑和替代方案，最后权衡各方建议形成共识
> ```
