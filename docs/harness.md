# harness

> [!IMPORTANT] 最重要一点
> 给`Claude`验证工作方式，以便能够让它根据验证流程进行改进，最终产出质量翻倍，因此需要把精力放在验证机制做扎实，这样投资回报率最高。

## plugins/skill/agents/workflow/scripts

- plugins 用于编排一系列 `skill`、`agent`
- skill 用于拓展专业技能
- agent team 协作 agent 流程可沉淀和规则
- sub agent 用于快速解决任务，沉淀不了规则和流程
  三者都可以自动触发和手动触发。
- workflow 用来编排**流程**避免agent遗漏某些流程的执行（harness）
- scripts 用来解决agent依靠硬prompt遗忘和不遵守问题

::: tip 插件和skill参考

[official-plugin](https://github.com/anthropics/claude-plugins-official/tree/main)

[officialMember-skill](https://github.com/ComposioHQ/awesome-claude-skills)

:::

## LSP

`LSP`一种开放协议，定义IDE与LLM之间的通信标准。`-lsp`添加的时候提供了整个项目的地图和语言级语义分析，为`LLM`提供项目索引、符号查询、依赖追踪等，使得能够精确跳转定义、查找引用等。

而且没有`-lsp`的时候，想要定义到具体逻辑的时候，`LLM`会去搜索文件，以此找到相关逻辑和影响，但这很可能会漏掉依赖特别是模块间依赖，同时会去加载整个项目导致思考时间长Token使用多(没有特定按需加载，也就是只加载对应模块和代码)，造成逻辑缺失。

::: tip 提示
`-lsp`前面加上`-`，这里是指的是已经提供了`LLM`的特定场景支持。例如`typescript-lsp`等等。
:::

## 总线型团队模式

::: warning 单体AI开发缺点
原始传统单体AI承担多种不同领域任务，被施加上了过多期望，同时还受到上下文限制、注意力限制的问题，导致任务处理变得降智，同时解决多种不同任务会参杂多种知识，逻辑紊乱造成逻辑断层。

这种模式缺点在复杂任务处理时非常明显，当对话超过上下文时模型会尝试去压缩上下文，导致原始上下文具体细节缺失以及逻辑变得模糊，最终使得任务处理效果不好。
:::

因而在复杂任务处理场景下可以使用`总线型团队模式`，类似网络架构设计中`总线`，具体使用如下:

```md
prompt:
【具体需求】, 创建并初始化以下4个sub agent，
其中架构师负责需求分析、技术选型、生成计划，
构建师负责代码编写、依赖管理,
验证者负责编写测试用例、bug追踪充当项目质量门禁，
最后是记录员负责编写使用说明、API文档。
```

::: tip 提示
这里的`总线型团队模式`是AI充当主节点对任务进行拆解、分发给不同特定领域`sub agents`每个agents负责处理特定任务、处理完后最后进行汇总。

但是这种模式的使用token成本很高，传统只有一个AI消耗token，现在变成了好几个，token使用翻好几倍。

:::

## 开发闭环

::: tip 重要
开发流程要重视**测试闭环**，也就是

```md
┌─────────────┐
│ 开发 │ ← authority + role + constraint
└──────┬──────┘
│
▼
┌─────────────┐
│ 测试 │ ← test（自测命令、验证步骤）
└──────┬──────┘
│
▼
┌─────────────┐
│ 验证 │ ← 检查输出是否符合预期
└──────┬──────┘
│
▼
┌─────────────┐
│ 优化 │ ← iteration（分析失败、调整策略）
└──────┬──────┘
│
└──────► 回到开发，直到通过
```

在准备开始写代码之前，生成的计划书中要第三人去审查避免单个AI主观因素影响造成细节和环节的遗漏，例如`审查这个计划文件`。这些文档最好物理存储，如果上下文被压缩之后文档具体细节和方案就会缺失，存储之后每次AI写完代码上下文不够压缩的时候，就可以根据这些文档继续下一步方案。

主要注意的就是还要`Git`可回溯，当前实施进度，避免中途开发跑偏(任务规划师)。还有一点就是在闭环中AI去修复代码时，需要明确一点**同时修复后必须验证问题已经解决，不能只改代码不测试**。

:::

::: warning 注意
上述过程跳过了`PRD`直接到开发技术文档(实施方案)，实际上需要进行需求验证验证**可行性**，然后在是技术选型、方案设计、实施方案。
:::

::: danger 危险
在进行迭代修复和自我改进过程中，可能会遇到报错问题，此时需要明确禁止它盲目重试，这里可以先让AI进行修复**2-3**次之后，后面还报错的话，就必须让它**停下来**思考并分析具体原因，然后再执行循环迭代过程。
:::

同时在AI编写完代码之后如果不想手动执行代码格式化工作，可以在`.claude/settings.json`中`claude hooks`定义相关hooks，例如在AI修改文件之后自动格式化代码:

```json
{
   "hooks": {
      //工具执行后使用
      "PostToolUse": [
         {
            "matcher": "Write",
            "hooks": [
               {
                  "type": "command",
                  "command": "pnpm run format"
               }
            ]
         }
      ]
   }
}
```

## 迭代循环安全

在使用Ralph Wiggum插件去基于开发流程循环进度开发的时候，默认是无限制迭代直到任务完成。

这样会不安全，特别是如果当它陷入到思考回环的时候特别危险，因此实际上操作使用时会限制循环迭代次数。

命令选项:

- `max-iterations <n>` -在n次迭代后停止
- `--completion-promise <text>` -标识完成的短语
- `/cancel-ralph` -手动取消循环

同时还需要确认完成标准，包含清晰完成条件和输出完成标准以及失败后的处理(卡住时的处理方法)，例如

```markdown
# cli使用

/ralph-loop "参考task.txt文件的详细需求" --max-iterations 20 --completion-promise "COMPLETE"

## task.txt

完成功能 X.

需求:

- 功能必须做 A, B, C
- 所有测试必须通过
- 代码覆盖 > 80%

如果15轮循环还是没有完成:

1、记录失败的内容：

- 你试过了什么？
- 具体错误消息
- 为什么你认为它失败了

2、研究替代方案

- 查找2-3个类似的实现
- 请注意使用不同办法

3、问题基础

- 这个抽象层次是否恰当？
- 这可以拆分为更小的问题吗？
- 有没有更简单的办法

4、尝试不同的角度

- 不同的库/框架功能？
- 不同的架构模式?
- 能否减少抽象而非增加？

**关键原则**

- 及时止损：不要重复相同失败
- 增量学习：每次失败都有记录
- 方向切换：从"加法"转向"减法"或"换法"

输出 <promise>COMPLETE</promise> 当完成的时候.

## 注意事项

上述cli使用之所以要在文件中列出详细需求，主要就是解决和避免包含换行符时，这个Ralph-loop插件在处理多行提示词时会触发安全错误
```

## 规则

[参考](https://github.com/TTT1231/claude-rules)

这里的规则是指在`claude.md`这样的系统提示词文件中，本质上是提示词工程。这个文件`claude.md`最好使用XML标签格式，因为官方示例在广泛使用，主要是XML标签提供清晰的层次结构，让claude能够识别不同规则的边界和作用域，也是解决在全局的`claude.md`中内容非常多的时候，XML标签让规则更容易定位、修改和调试。也即`XML+Markdown`这种格式最好。

::: tip 提示
这种适合在一个`CLAUDE.md`中内容特别多情况，别过度嵌套了XML结构，保持单层扁平即可，同时标签名称也别过长或含糊不清。

如果比较简单的话，就可以不用，直接使用markdown格式就可以了。
:::

当所有内容都嵌入了在一起导致`CLAUDE.md`内容很多，claude提供了`.claude/rules/`目录来解决这个问题。例如错误教训规则，使用如下:

```md
.claude/rules/
├── errors-learn/
│ ├── typescript-errors.md
│ ├── vue-errors.md
│ ├── api-errors.md
│ └── database-errors.md
└── testing.md
```

使用时直接在`CLAUDE.md`导入这条规则即可`TypeScript @.claude/rules/errors-learn/vue-errors.md`。

::: warning 注意
文件导入文件在导入文件规则为递归导入，默认最大深度为5层。

要根据项目所有技术栈相关程度，按照规则**优先级**进行导入和标记，例如标记高优先级错误经验规则:

```md
## [高优先级] 错误经验规则名称

原因: ....
解决: ....
预防: ....
```

然后将这个错误经验规则按需导入到项目的CLAUDE.md配置中即可`@.claude/rules/[path]/[to]/[target].md`

:::

## 过度多专家分工设计负债问题

在当前Agent领域"大而全"趋势下，如果违背了工程化落地的核心原则：解决实际问题的最小可行性方案，远胜于功能复杂但增加更多失败点的方案。这种复杂性不是价值，而是技术负债。

主要体现在多Agent调试成本指数增长，各Agent上下文被隔离传递时只保留了执行消息，同时开发时支持了所有场景和架构过度设计造成：学习成本陡峭、后续维护和迭代更慢。

因此实际好的设计应该时使用最小部件，稳定地解决真实问题，以解决任务为导向。

::: tip 提示
因此应该根据问题复杂度选择合适方案，大多数任务单Agent+skills就比多Agents协作更高效。也就是实用主义优先。

如果是阶段任务例如A、B、C可以任务并行而且任务边界清楚就可以用到多Agents，每一个agents负责对应任务互不干扰。
:::

## worktree

`Git Worktree` 允许在同一个仓库中检出多个分支到不同目录，而后管理这个`worktree`目录即可，在这个目录中跟`Git`一样使用即可，最后在合并到主分支即可。

claude结合`worktree`可以实现并行任务并发，从而单个任务失败或者成功在不合并到主分支之前，对主分支不会造成任何影响。

**基础命令**

| 命令                                        | 描述                       |
| ------------------------------------------- | -------------------------- |
| `git worktree add .trees/[feature-name]`    | 创建新的 worktree          |
| `git worktree list`                         | 列出所有 worktree          |
| `git worktree move <old> <new>`             | 移动 worktree 到新位置     |
| `git worktree remove .trees/[feature-name]` | 删除 worktree 及其引用     |
| `git worktree prune`                        | 清理已删除的 worktree 引用 |

**完整工作流示例**

假设需要同时开发两个独立功能：用户认证和支付集成

```sh
# 步骤1: 创建两个 worktree
git worktree add .trees/feature-auth -b feature/auth
git worktree add .trees/feature-payment -b feature/payment

# 步骤2: 查看已创建的 worktree
git worktree list

# 步骤3: 分别在两个终端中打开 Claude，针对不同目录工作。在各自worktree中正常使用Git等命令。

# 步骤4: 功能完成后，合并回主分支。然后清理已完成的worktree
```

**工作流最佳实践**

::: tip 提示

1. **统一目录命名**: 使用 `.trees/` 前缀组织所有 worktree，方便管理
2. **及时清理**: 任务完成后及时删除 worktree，避免累积过多目录
3. **独立终端**: 每个 worktree 使用独立的 Claude 终端，避免上下文混乱
4. **原子性**: 每个 worktree 专注单一功能，保持任务边界清晰
   :::

::: warning 注意
手动删除分支文件之后，分支引用还是会存在，这是还需要去git中删除这个分支引用。

`git worktree remove .trees/[feature-name]`。

最后别忘了分支还是存在的，还是需要手动去删除`git branch -d .trees/[feature-name]`
:::

## 重新规划计划

::: tip 核心原则
遇到问题时，**Claude 先自我审查判断严重程度**。如果是小问题，自主尝试修复 3-4 次（每次必须用不同方法）；如果判断无法修复，直接进入 **plan** 模式，重新探索新的方向，避免在错误方向死磕。修复失败后再由人介入决策。
:::

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  步骤1：创建终端
  ┌─────────────────────────────────────────────────────────────────┐
  │  人类根据任务复杂度决定终端数量：                               │
  │                                                                 │
  │  简单任务 → 开 1 个终端（终端 A）                               │

  ┌─────────────────────────────────────────────────────────────────┐

  │  终端 A 执行：                                                   │

::: tip 自主修复的关键规则

-  4. 3-4 次后仍失败 → 必须暂停，不要再试（大概率是方向出错因此需要及时止损）

└─────────────────────────────────────────────────────────────┘

错误示例：
┌─────────────────────────────────────────────────────────────┐
│  第 1 次：修改参数                                          │

│                                                             │

│  → 失败                                                     │
│                                                             │
│  第 3 次：继续调整参数                                      │
│  → 失败                                                     │

- ✅ 每次尝试明确说明使用的方法和理由
- ✅ 尝试修复完成更新`CLAUDE.md`文档
- ✅ 遇到方向性问题直接进入 plan
- ✅ 修复后必须验证问题已解决

## 提示技巧

让AI扮演严格的**代码审查者**角色，让它“质疑你的决策”，让AI主动找问题、挑毛病而不是等了出错了在修复，把质量保证阶段落地到开发阶段。或者告诉它，证明给你看，这行得通，同时有实际的对比效果相较之前，例如缓存分支与主分支相比是否提升了性能。

::: code-group

```md [code-inspector.md]
你是我的缓存分支功能的**严格代码审查员**。请按照以下流程审查我的改动：

═══════════════════════════════════════════════════════════
第一步：代码审查
═══════════════════════════════════════════════════════════
阅读缓存分支上的所有改动挑战我的设计决策，找出

- 潜在bug和边缘情况
- 安全问题（如缓存穿透、雪崩）
- 性能瓶颈
- 代码可维护性问题
- 其他我没有考虑到的情况和问题，例如并发场景下的缓存一致性问题、缓存失效策略是否合理、Redis连接池配置是否优化合理等等

═══════════════════════════════════════════════════════════
第二步：效果验证
═══════════════════════════════════════════════════════════
1、对比main和缓存分支，运行相同测试记录结果
2、对比两者的差异，证明缓存确实生效例如缓存事件是否显著降低、命中与未命中行为是否符合预期、数据一致性是否保持一致

═══════════════════════════════════════════════════════════
第三步：最终结论
═══════════════════════════════════════════════════════════
只有满足以下条件才允许我提交PR：

- [] 所有严重问题已修复
- [] 性能提升有数据证明
- [] 缓存行为验证通过

---
```

:::

如果针对一个需求，在采取了不尽如意的补救措施，还是达不到现有的效果，直接进行**解决方案回退**。例如：“鉴于你现在所掌握的所有信息，放弃这个方案，实施更优雅的解决方案”，避免在一个错误方案上越走越远，浪费token。

::: tip 提示
在准备推送到生产仓库之前，应该要编写详细的规范并减少歧义。越具体，最后的更改成本就越少。
:::

## agent teams 协作

多智能体协作，在使用时需要考虑的是使用场景，什么场景下需要什么场景下又不需要。由于多agent teams在工作
时会通过主lead进行任务分发并统筹team的工作任务下发和任务进度的推进工作，因此如果任务太小的话那么会存在主lead协调
开销，此时速度就会慢一些而且协调工作意义不大。

还有一种情况就是大任务直接进行工作，例如重构整个代码库，这样
长时间独立工作如果方向错了或者claude遇到没有注意的情况会浪费大量时间和token。

创建agent的时候也需要考虑最小agent单元（最小团队规模），每一个agent专注一个特定领域，除了一些辩证和急需纠错、纠缺陷的场景。

::: tip 提示
因而最重要的是就是要明确最小交付物的独立单元，也就是任务独立完成不依赖其他完成工作并且同时还能
够完成后就能看到具体结果和快速检查是否完成正确。

让每个agent保持更加高效，结合官方文档任务5-6个就可以了。

任务开始时，可以`Ctrl + T`查看任务执行清单。
:::

::: warning 注意
分配太多任务的话，会增加主lead的协调负担，特别是在某个agent卡住的时候会让重新分配变得很困难。
同时任务越多token使用也会越来越多。

同时在权限配置中，主lead应该只关注任务的推进情况，只做协调者和分配者，不做执行者，这样让职责更加清楚和明确，
因此在开发时注意开启委托模式。

工作完成后要及时清理团队资源，否则会浪费token。
:::

> [!IMPORTANT] 最佳使用场景
> 在一些问题处理中，如果遇到问题找不到一个合理解决方案时就可以使用**辩证理论**，这样就很大程度上
> 避免了单个agent陷入思维定势，让不同agent从不同视角去分析问题并彼此之间相互论证，在假设不断被互相推翻的时候留下
> 来的假设往往是解决方案，这样就使得错误更早被发现减少单一视角的局限性错误。
>
> **例如:**
>
> ```md
> 创建一个agent teams去审查缓存功能，生成三个审查者进行审查:
>
> - 一个注重安全影响
> - 一个检查性能影响
> - 一个验证测试覆盖率
>   各自审查并报告结果。
> ```
>
> **彼此论证:**
>
> ```md
> 创建一个agent teams去审查缓存功能，生成三个审查者进行审查:
>
> - 一个注重安全影响
> - 一个检查性能影响
> - 一个验证测试覆盖率
>   各自先审查并各报告各领域发现的问题和改进建议，然后彼此质疑交叉论证并提出顾虑和替代方案，最后权衡各方建议形成共识
> ```

## Agent标准与Claude的差异

本节主要介绍 `AGENTS.md` 与 `CLAUDE.md`、以及 Agent Skill 与 Claude Skill 之间的差异，包含以下两方面：

- **Agent Skill 与 Claude Skill** 区别
- **Agent README** 区别

### Skill 区别

::: tip 架构差异
Agent Skills 标准，它会把skill定义为目录，这样通用性更强，但是创建成本更高，而且更加规范性没有灵活性，不过却更加通用。

agent skills在初始的时候会有标准的**三次**加载，

- 首先读取 `SKILL.md` 的 frontmatter 元数据，判断当前上下文是否应激活该 skill
- 其次是当skill被激活的时候会加载`SKILL.md`的内容
- 最后根据`SKILL.md`的内容，按需加载(scripts/、 references/、 assets/ )

```
skill-name/
├── SKILL.md # 必需：元数据 + 指令
├── scripts/ # 可选：可执行代码
├── references/ # 可选：参考文档
├── assets/ # 可选：模板、资源
└── ...
```

claude skill纯靠语义理解，它有专门的`frontmatter`进行验证，因此不需要严格的元数据就能精准触发和匹配，而且它采用的是**单文件结构**，因此能够快速创建，但是只适配claude移植性很差，同时它还有它专门的特性。

claude skill 只有**2次**加载，

- 首先是加载skill的name和description匹配和用户主动选择
- 然后skill加载后一次加载完整个的`SKILL.md`中的所有内容

```
.claude/skill-name/
└── SKILL.md
```

:::

::: tip 特性区别

标准的agent skill只有以下字段：

```md
| 字段          | 是否必需 | 约束条件                                                             |
| ------------- | -------- | -------------------------------------------------------------------- |
| name          | 是       | 最多 64 个字符。仅限小写字母、数字和连字符。不能以连字符开头或结尾。 |
| description   | 是       | 最多 1024 个字符。不能为空。描述技能的功能及使用时机。               |
| license       | 否       | 许可证名称，或对捆绑的许可证文件的引用。                             |
| compatibility | 否       | 最多 500 个字符。指明环境要求（目标产品、系统包、网络访问等）。      |
| metadata      | 否       | 用于存放额外元数据的任意键值对映射。                                 |
| allowed-tools | 否       | 空格分隔的字符串，列出技能可使用的预批准工具。（实验性特性）         |
```

而claude拥有以下特性：

```md
| 特性                       | 作用说明                                                             |
| -------------------------- | -------------------------------------------------------------------- |
| `model`                    | 为 Skill 指定特定模型，简单任务可用最快模型执行                      |
| `effort`                   | 控制思考深度，困难任务可设置为 `max` 使用最大思考深度                |
| `context: fork`            | 新建独立会话执行 Skill，防止主对话上下文 token 爆炸                  |
| `agent`                    | 指定由哪个子代理（Agent）来执行该 Skill                              |
| `user-invocable`           | 控制用户是否可以主动调用该 Skill                                     |
| `disable-model-invocation` | 禁止模型自动触发 Skill（仅允许用户手动调用）                         |
| `argument-hint`            | 调用 Skill 时显示的参数提示（如 `[version]`）                        |
| `hooks`                    | 在 Skill 执行期间（前/后/出错时）触发特定行为                        |
| `!` 插值命令               | 在 Skill 正文中嵌入命令，执行时自动插入命令输出结果                  |
| `allowed-tools`            | 允许 Skill 使用的工具及命令权限控制（支持 `Bash(git:*)` 等精确过滤） |
```

这些特性与claude深入集成，但移植性很弱，这里主要是为了解决标准agent skill的**api成本问题**还有**上下文窗口问题**、**用户体验问题**、**权限问题**。
:::

### Agent README 区别

`AGENTS.md` 是给通用 AI Agent 的 README，类似项目的 `README.md`，而 `CLAUDE.md` 是专门给 Claude 使用的。

::: tip 提示
通用 AI Agent 包括 Codex、Cursor、Claude 等，`AGENTS.md` 作为通用配置文件，每个 Agent 都可以识别它。而各个 Agent 也有自己专属的配置文件，例如 Claude 的 `CLAUDE.md`。

`CLAUDE.md` 支持 Claude 特有的 `@` 导入语法，Claude 解析到 `@` 路径后会递归加载对应文件，将内容内联展开到 `CLAUDE.md` 中作为项目指令加载。例如在 `CLAUDE.md` 中写 `@../AGENTS.md`，就会把 `AGENTS.md` 的内容完整注入进来。
:::

## Git 即事实源

Git 本身已经是一套完整、可信的事实记录系统。**不要再自造状态文件去复述 Git 已经记下的东西。**

::: tip 一句话根因
Git 的记录是**伴生**的——代码一动它就自动记，零维护、永远跟代码一致；人造状态文件是**维护**的——你要主动记、主动同步，多一道手续就多一个出错点。**费力维护的人造副本，永远比不过自动伴生的原版。** 与其再造，不如直接用 Git。
:::

::: details 编排 AI 时踩过的七个坑（复盘）
为了让流程显得"更可控、更严谨"，编排 AI 时很容易自造一整套状态记录 + 机制层防御。每一条单看都"有道理"，真用起来全是坑，逐个复盘：

**坑 1：用 JSON 记录每步进度（类似 `run-state.json`）**

- **想做**：把"做到第几个任务、每个任务什么状态"写进 JSON，上下文丢了能从它恢复。
- **实际**：`git status` 已经告诉有没有未提交改动，任务清单勾选已经告诉做到哪。这个 JSON 还得**每做完一步就同步更新**，一旦忘更新就脱节——文件说"做到第 5 步"，Git 说"其实只改了 3 个文件"，两个真相打架。它唯一的用途就是跟 Git 重复，删了。

**坑 2：给每个任务打锚点标记（类似 `openspec/<change>/baseline`、`task-<i>` tag）**

- **想做**：给每个任务打唯一标记，好算"这个任务当初碰了哪些文件""那个任务的改动波及了谁"。
- **实际**：Git 的 commit 历史 + tag 本来就是锚点，按时间线就能对应任务。造的锚点要跟 commit 一一对应，**对不齐就全乱套**（任务 N 到底对应哪个 commit？）。维护这套对应关系比直接看 `git log` 还累。

**坑 3：追踪任务之间的改动影响（类似 dirty 计算）**

- **想做**：改任务 F 时，算一算会不会波及前面已完成的任务 A–E，提前标记需要重新验证的。
- **实际**：要算"波及谁"，得先有每个任务当初碰了哪些文件（依赖坑 2 的锚点）。锚点维护不住，这个计算也跟着崩。**而且根本不需要算**——代码错了，最后的测试自然挂，失败日志直接指出哪个文件、哪个用例的问题，比提前算"波及谁"准得多。

**坑 4：全量验证兜底（类似 final validation）**

- **想做**：所有任务做完，最后跑一遍全量 test/build/e2e 当安全网。
- **实际**：任务清单的最后一步**本来就是**"跑测试/验证"这个 gate，代码错了这一关会挂。在它之上再叠一道机制层重跑就是重复劳动；而且 e2e 慢的话，全量重跑很贵——不如让那个验证 gate 自己限定只跑本次改动相关的子集。

**坑 5：每个任务过检查门才允许提交（类似 commit 闸门）**

- **想做**：任务全勾了 + git 有改动才能 commit，防止"假完成"（勾了但没写代码）。
- **实际**：假完成会被自然暴露——后续依赖它的任务做不下去、最后的测试挂、勾选数和 git diff 数对不上，三道天然屏障已经抓住了。而且一个 change 往往 20 个任务，每个都过闸门 commit 一次 = 20 个细碎 commit，commit 疲劳，不如一次性做完。

**坑 6：给任务分类、加特殊勾选规则（类似 checkpoint 机制）**

- **想做**：区分"写代码的任务"和"跑测试的任务（checkpoint）"，给 checkpoint 加规则"跑过且通过才勾"。
- **实际**：跑测试本身就是个任务，跟写代码同级——为了勾它就得跑，不需要额外分类。"分类"这个动作还会诱导去想"哪个 checkpoint 验哪个任务、它们怎么连"，一不小心又往坑 3（dirty）的方向滑。

**坑 7：开工前给每个任务生成执行摘要（类似 execution brief）**

- **想做**：每个任务开始前生成一份摘要（干啥、涉及哪些文件、预计改哪些代码），帮 agent 对齐。
- **实际**：摘要里的每个字段都是已有信息的重新排版——任务描述抄自任务清单，涉及文件 agent 动手时 LSP 一查就知道。**它不增加任何新信息，只是把读过的东西又抄一遍**，纯仪式，删了。

**共同病因**：这七条全是同一个病——在 Git 已经伴生记录的事实之上，再叠一层需要人工维护的副本。Git 随代码自动记，零维护、不会错；人造的要主动同步，多一道手续就多一个出错点。努力越多，维护负担越重，效果反而不如直接用 Git。

**结论：全删，只留 Git。** 进度、改动、回溯、影响判断，全交给 Git + 后续任务 + 测试这三道天然屏障。
:::

自造文件想记的东西，Git 原生全都有：

| 你想记的     | Git 命令                             |
| ------------ | ------------------------------------ |
| 当前做到哪   | `git status` + 任务清单勾选          |
| 改了哪些文件 | `git diff --name-only`               |
| 改了什么内容 | `git diff`                           |
| 改动历史     | `git log`                            |
| 回溯某刻代码 | `git show <commit>` / `git checkout` |
| 做错了想回滚 | `git reset` / `git checkout`         |

::: tip AI 上下文恢复
聊天上下文被压缩/清空后，AI 丢失了"做到哪了"的记忆。这时**不要靠聊天记忆，也不要靠自造状态文件**（可能已脱节），直接看三个 Git 事实：

1. `git status` —— 有没有未提交改动（做到一半的活）
2. `git diff` —— 未提交改动是什么（正在做什么）
3. 任务清单勾选 —— 哪些任务已完成、对应哪些已提交的代码

三个加起来完整重建进度，零维护成本。
:::

::: warning Git 是"记录器"，不是"防御器"
Git 只记录**发生了什么**（改了啥、何时改的、当前什么状态），不负责**该不该改、改对了没**——那是测试和人工审查的事。

编排 AI 流程时，别往 Git 之上叠"防御机制"（每个任务过检查门才提交、算改动影响、最后全量重验）。这些想防的问题，后续任务和测试这两道天然屏障已经能抓到——叠机制只会增加复杂度。
:::

**一句话：Git 是唯一可信的事实源，不要自造第二真相源。进度、改动、回溯，全从 Git 查。**
